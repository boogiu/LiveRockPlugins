# Agent Orchestration

## 이 스킬이 지금 담당하는 범위

Paseo로 워커 하나를 실제로 기동하고 결과를 돌려받는 데 필요한 최소 절차만 담는다 —
전제 점검, `create_agent`에 넣을 값 구성, 워커 브리핑, 결과·실패 파일 규약. **레벨 판정,
활성·대기 큐 운영, 재시도, 검토 분리, 실행 기록은 아직 없다** — 이후 단계에서 이 스킬에
이어 붙인다. 지금은 워커를 하나씩, 또는 사용자가 명시한 여러 개를 그때그때 기동하는 데만
쓴다.

## 1. 전제 점검

### 연결 확인

Paseo MCP 도구(`create_agent`, `send_agent_prompt`, `get_agent_status`, `list_agents`,
`cancel_agent`, `list_workspaces`)가 이 세션에 붙어 있지 않으면 연결이 불충족이다. 그
사실을 명확히 보고하고 사용자 전역 config를 스스로 고치지 않는다. provider를 추측하지
않는다. (`daemon.mcp.injectIntoAgents`가 활성이어야 새 세션에 Paseo 도구가 주입된다.
기본값은 false다.) 연결이 실패하면 이미 승인된 범위 안에서 복구하고, 복구할 수 없으면
필요한 설정 변경을 구체적으로 제시해 사용자 판단을 받는다.

사용자 판단을 받은 뒤에만 `paseo run`의 `--provider`·`--mode`·`--thinking`으로 기동한다.
기동 후 응답·`inspect`의 `thinking`/`currentModeId` 값을 요청값과 대조해 적용 여부를
확인하고, 확인됐는지 못 했는지를 완료 보고에 적는다.

### 워크스페이스를 고른다

`list_workspaces`로 조회해 `cwd`가 대상 저장소인 워크스페이스를 고르고, 그 `workspaceId`를
`create_agent`에 명시한다. 생략하면 새 워크스페이스가 만들어진다. 워크스페이스 ID를
하드코딩하지 않고 매번 조회한다.

결과 파일을 서로 읽어야 하는 작업들은 같은 워크스페이스에 둔다. worktree 격리는 사용자가
명시할 때만 쓰고, 그때는 각 worktree 경로를 받아 그 경로를 읽어야 하는 워커의 브리핑에
넣는다.

이 호스트에서 쓸 수 있는 완료 알림·대기 수단을 확인하고, 없으면 종료 확인에
`get_agent_status`·`list_agents`의 제한된 상태 조회를 허용한다.

## 2. create_agent에 넣을 값 구성

`create_agent`에는 프로필을 지정하는 인수가 없다. provider·model·mode·thinking을 직접
정해서 넣는다 — 저장된 프로필이 있으면 그 값을 옮기고, 없으면 `list_providers`·
`list_models`로 조회해 이번 실행에 쓸 값을 직접 구성한다. 프로필은 있으면 편하게 옮겨
쓰는 재사용 수단일 뿐, 워커를 기동하는 데 반드시 있어야 하는 것은 아니다.

어느 경로로 값을 정했든 아래 대응을 그대로 따른다.

| 정한 값 | `create_agent`의 자리 |
| --- | --- |
| `provider` + `model` | `provider` — 두 값을 `provider/model` 한 문자열로 합쳐 넣는다 |
| `modeId` | `settings.modeId` |
| `thinkingOptionId` | `settings.thinkingOptionId` |
| `featureValues` | `settings.features` — **이 값이 있을 때만** 옮긴다. 없으면 `settings.features`를 넣지 않는다 |

- `workspaceId`를 명시한다(1절).
- `title`은 `{역할 또는 프로필 이름}: 한 줄 요약`, `labels`는 `{"task": 한 마디, "run": 실행
  식별자}`. 프로필을 썼으면 `labels.profile`에 프로필 id를 더한다. `run`은 이번 실행을
  가리키는 식별자로 `{YYYY-MM-DD}-{슬러그}` 형식을 쓴다. `title`은 60자 상한이므로 그 안에서
  만든다.
- `settings.modeId`는 스키마상 선택 필드지만 채우는 것을 기본으로 둔다. 정한 값을 그대로
  옮긴다.
- 실제 모드·모델·thinking은 요청값이 아니라 기동 결과로 확인한다. 모드는 `create_agent`
  응답의 `currentModeId`를 요청값과 대조한다. 모델과 thinking은 `snapshot.model`·
  `snapshot.effectiveThinkingOptionId`로 확인한다. `runtimeInfo`는 쓰지 않는다. 워커가
  하나면 `create_agent` 직후 `get_agent_status` 1회, 여럿이면 전체 기동 후 `list_agents`
  1회로 한꺼번에 대조한다. 호출 수가 워커 수에 비례하지 않게 한다. 보고의 "모드"·"모델"
  줄에는 확인한 값을 쓰고, 요청값과 다르면 출처를 적는다.
- 결과 파일을 써야 하는 워커에는 계획만 내고 파일을 쓰지 않는 모드(예: claude의 plan
  모드)를 고르지 않는다.

## 3. 워커 브리핑

`assets/worker-briefing.md`가 그 템플릿이다. 워커를 띄우기 직전에 읽고 중괄호 자리를
채워 `initialPrompt`로 넘긴다.

반드시 싣는 것:
1. 워커 신분과 세션 내 재위임 금지
2. 이번 작업을 위해 정한 역할 — 프로필을 썼으면 그 이름과 `notes` 원문, 아니면 구성한
   역할 설명 한 줄. 첫 줄 고정 형식은 `assets/worker-briefing.md`를 따른다
3. 작업 목표, 수정 가능 대상, 사용자 확정 제약
4. 담당 원본 합격 기준 — 네가 요약한 것이 아니라 원본을 옮긴다
5. 필수 입력 경로
6. 결과 보고 경로와 실패 보고 경로(둘 다 네가 지정한다)
7. 도구와 권한 예외 — 셸은 기본 도구로 실행하고 터미널을 새로 만들지 않는다
8. 출력 크기 제한
9. 보고 형식

싣지 않는 것:
1. 역할·프로필 선택 이유와 모델 비교
2. 큐 운영과 계획 승인 절차
3. 다른 워커의 작업과 참고 배경
4. 같은 제약의 반복
5. 미승인 제안
6. 경로로 제공한 앞 산출물의 본문

사용자 대화에만 있는 제약은 브리핑에 싣는다. 미확정 요청과 질문의 대안은 미확정 입력으로
표시하고 실행 지시나 확정 제약으로 취급하지 않는다.

전체 대화와 산출물 본문은 다시 보내지 않는다. 글자 수 때문에 포함 목록 항목을 빼지 않는다.
추가 맥락은 빠지면 실행이나 판정이 달라지는 경우에만 싣는다. 프로필을 썼으면 그 `notes`는
요약 없이 원문을 한 번만 싣는다. 새 브리핑 문서는 만들지 않는다.

## 4. 결과 파일 규약

결과는 완료 알림 본문이 아니라 파일로 받는다.

완료 알림에는 결론, 수행 범위, 해당 핵심 실행 증빙, 핵심 근거, 제약, 해당 결과 경로를
짧게 적고 해당하지 않는 항목은 생략한다. 출력 제한 때문에 사용자 요구 데이터나 합격 판정
근거를 빼지 않는다. 긴 텍스트 산출은 별도 결과 파일에 필요한 부분과 위치를 보존하고, 파일
수정 자체가 결과인 작업은 별도 성공 보고 파일을 만들지 않는다.

- 조사·분석처럼 결과가 텍스트라면 실행 디렉터리를 정한다: `.agents/orchestration/{날짜}-
  {슬러그}/`. 날짜는 실행일의 `YYYY-MM-DD`이고 슬러그는 이번 실행 전용 값이다. 같은 경로가
  이미 있으면 슬러그를 바꿔 새 디렉터리를 고른다. 조사·분석·판정 결과는 워커마다
  `nodes/{워커 식별자}.md`, 실패 보고는 `nodes/{워커 식별자}.failure.md`에 쓰게 한다 —
  반드시 서로 다른 파일이다. 경로는 네가 정해 브리핑에 명시한다. 스킬 소스에 사용자의
  고정 경로를 하드코딩하지 않는다 — 실행 중에는 선택한 workspace 기준 상대 경로로
  해석한다. worktree 간 전달이나 호스트가 절대 경로를 요구할 때는 조회로 확인한 실제
  절대 경로를 그대로 전달한다.
- 결과가 파일 수정 그 자체라면 성공했을 때 쓸 별도 결과 파일을 만들지 않는다. 그래도
  실패 보고 경로는 지정한다 — 같은 실행 디렉터리의 `nodes/{워커 식별자}.failure.md`다.
  성공하면 그 파일이 생기지 않고, 파일이 있으면 그것이 실패다.
- 수정 대상 파일에 실패 사유를 쓰게 하지 않는다. 실패 사유는 언제나 실패 보고 경로로 간다.
- 파일 기록이 불가능하거나 사용자가 쓰기를 금지한 경우, 워커는 파일을 쓰지 않고 짧은
  응답으로 실패와 미검증을 보고한다. 그 응답을 실패 보고로 본다.
- 결과 파일 본문을 네 컨텍스트로 옮기지 않는다. 판단이 필요할 때만 알림 요약을 읽고,
  부족하면 결과 파일을 범위를 제한해 읽는다.
