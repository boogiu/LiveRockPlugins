# 실패·재시도·재개

노드가 실패했거나, 재시도·쿼터 소진·권한 대기·사용자 중단·레벨 1·2 재개를 판정할 때
읽는다. 10절이 이 문서를 언제 읽는지를 정하고, 읽은 뒤의 동작은 이 문서가 정한다.

이 문서와 현재 호스트 정책이 어긋나면 **호스트 정책을 따른다.** 스킬 절차로 권한을 올리거나
실행 중 메시지를 강제하거나 전역 config를 고쳐 우회하지 않는다. 막히면 그 사실을 보고한다.

종료(에이전트가 멈춤)와 합격 기준 통과는 다르다. 멈춘 것만으로 `완료`로 쓰지 않는다.

실행 디렉터리는 `.agents/orchestration/{YYYY-MM-DD}-{슬러그}/`이고, 노드 결과 파일은
`nodes/{노드 ID}.md`, 실패 보고는 `nodes/{노드 ID}.failure.md`다. 단계 산출물은 실행
디렉터리 바로 아래 `QUESTION.md` 하나뿐이다.

## 실행 기록 쓰기 실패

실행 디렉터리 생성이나 `GRAPH.md` 쓰기가 실패하면 — 권한 거부, 쓰기 금지, 경로 오류 어느
쪽이든 — 그 사실을 사용자에게 알린다. 이 실패는 실행을 멈추지 않으므로 알리지 않으면 워커는
그대로 도는데 기록만 없는 상태가 되고, 재개할 때 대조할 근거가 사라진다.

- 실패한 동작(디렉터리 생성인지 `GRAPH.md` 쓰기인지), 대상 경로, 호스트가 낸 사유를 적는다.
- **실행은 멈추지 않는다.** 남은 노드는 그대로 기동·판정하고, 기록에 남기지 못한 상태 전이는
  완료 보고에 싣는다.
- 권한을 올리거나 다른 경로로 바꿔 우회하지 않는다 — 경로를 바꾸면 재개가 찾을 자리가
  달라진다.

## 실패 보고 우선

완료 판정은 이 순서다. 앞이 뒤보다 이긴다.

1. 실패 보고 경로에 내용이 있으면 `실패`다. 결과 파일이 있어도, 에이전트가 정상 종료여도
   통과로 뒤집지 않는다.
2. 결과 파일 경로의 파일과 그 노드의 합격 기준 한 줄을 대조해 맞으면 `완료`.
3. 결과 파일은 있으나 합격 기준과 맞지 않으면 `실패`다. 자동 재시도하지 않고, 의존 노드는
   기동하지 않는다.
4. 에이전트는 끝났는데 실패 보고도 결과 파일도 없으면 원인을 특정하지 못한 실패로 보고하고
   재시도하지 않는다.

검토 노드는 위 1번 대신 아래 세 갈래 표로 갈음한다. 1번은 일반 노드에 그대로 적용된다.

| 상황 | 노드 판정 | 검토 라운드 | 자동 재시도 |
| --- | --- | --- | --- |
| 1. 검토 대상이 합격 기준 미달 | **성공** — 검토자는 맡은 일을 했다 | **1 소비** | 해당 없음 |
| 2. 환경적 중단 — 명령 실행 실패·permission 거부·도구 접근 불가로 검토를 끝내지 못함 | **실패가 아니다.** 상태를 `대기`로 되돌리고 진행 조건 칸에 `환경 미수행`과 사유를 적는다(새 상태를 만들지 않는다) | **소비하지 않는다** | 환경이 복구되면 같은 브리핑으로 재수행한다 |
| 3. 검토자 작업 실패 — 환경은 정상인데 기준을 잘못 읽거나 판정을 내지 못함 | **실패** | **소비하지 않는다** | **하지 않는다.** 즉시 멈추고 원인과 함께 사용자에게 보고한다 |

검토 라운드 상한은 총 2회다 — 최초 검토 1회와 재검토 최대 1회이고, 실제로 연 검토만 센다.

## 의존 차단

실패 판정은 확인 즉시 표에 기록하고, 의존 차단은 다음 단계를 기동할지 판단하는 시점에
적용한다. `실패` 노드에 의존하는 노드는 `paseo run`을 호출하지 않고 상태를 `대기`로 남겨
보고에 `미기동`으로 낸다. 의존하지 않는 같은 스테이지 노드는 3절 큐로 계속 돌린다.

부분 실패 보고: 노드별 상태(`완료`/`실패`/`미기동`) + 완료된 결과 파일 경로 + 무엇을 못 했는지.

## 이미 받은 승인

같은 요청·같은 범위에서 이미 받은 계획 승인, 되돌리기 어려운 작업의 승인, 워커 권한 `allow`는
다시 묻지 않고 재사용한다. 그래프 형태가 그대로인 재개에도 새 계획 승인은 없다. 범위가 바뀌면
9절·10절 게이트로 다시 받는다.

## 권한

- **대기** — 기존 승인 범위 안이면 다시 묻지 않고 재사용해 응답한다. 없거나 범위를 넘는
  요청만 원문 그대로 보여주고 사용자 결정을 받는다. 자동 승인하지 않는다.
- **명시 거부** — 재시도하지 않는다. `full-access`나 `sessionMode`로 우회하지 않는다.
  그 노드를 `실패`로 두고 보고한다.

부수효과가 없다는 이유만으로 거부를 재시도 가능으로 분류하지 않는다.

## 재시도

자동 재시도는 아래 두 조건을 **모두** 만족할 때만, **1회만** 한다. 무조건 재시도하지 않는다.
레벨 1·2 모두 `GRAPH.md` 노드 표의 `재시도` 셀에 `가능 · 한도 1 · 사용 N` 또는 `불가`를
적는다. 열을 늘리지 않는다.

**기동 재시도 예산과 검토 라운드 예산은 따로 센다.** 검토를 수행하지 못한 기동 실패는 검토
라운드를 소비하지 않는다. 수정 후 재검토는 기동 재시도 한도로 막히지 않는다.

**호출 전에 횟수를 기록한다.** 사용 횟수를 `GRAPH.md`의 `재시도` 셀에 반영한 뒤에만
`paseo run`을 다시 부른다. 호출 뒤에 적으면 기록이 비기 전에 한 번 더 호출된다.

**조건 1 — 워커가 작업 부수효과를 남기기 전에 죽었는가.**

| 재시도 가능 (자동 1회) | 재시도 금지 (보고하고 사용자 판단) |
| --- | --- |
| 기동 실패 — 프로세스·셸 생성 실패. **에이전트 미생성이 조회로 확인됐거나, 엔티티는 있으나 프로세스·셸 부수효과가 0임이 확인된 경우만** — 엔티티 상태를 기록하고 허용 횟수 안에서 재시도한다 | 워커가 작업을 시작한 뒤의 실패 (부분 실행) |
| 도구 인수 검증 실패 (리더가 인수를 고쳐 재호출). 생성 호출이 거절된 것이 응답으로 확인된 경우 | 합격 기준을 못 맞춘 실패 (같은 브리핑이면 같이 실패) |
| | 브리핑 결함으로 인한 실패 |
| | 검토자 작업 실패 (검토 노드 표 3번) — 즉시 멈추고 원인과 함께 사용자에게 보고한다 |
| | 원인을 특정하지 못한 실패 |
| | 권한 **명시 거부** |
| | 생성 결과가 **불명**인 전송·타임아웃 — 아래 「불명 생성」 |

**조건 2 — 그 노드가 멱등한가.** 설계 때 `재시도` 셀에 미리 적는다. 아래를 **전부**
만족할 때만 멱등이다.

- 결과 파일이 지정된 경로에 대한 쓰기·덮어쓰기뿐이다.
- git 커밋·푸시·태그·브랜치 조작을 하지 않는다.
- 외부 전송(메일·메신저·API POST·업로드)을 하지 않는다.
- 파일·디렉터리 삭제와 이름 변경을 하지 않는다.
- 저장소 밖 설정을 고치지 않는다.

하나라도 어기면 `불가`다. 실패하면 자동 재시도 없이 현재 상태와 무엇까지 실행됐는지를
먼저 보고한다.

부분 실행 여부는 셋을 함께 본다 — 결과 파일의 존재와 내용, 실패 보고 경로, `git status`의
작업 트리 변화. 하나라도 작업이 시작됐음을 보이면 재시도하지 않는다. 실패 보고가 있으면
이 항보다 「실패 보고 우선」이 이긴다.

기동이 실패해 활성 슬롯을 잡지 못했으면 그 작업은 슬롯을 점유하지 않은 것으로 본다.
브리핑 결함은 재시도하지 않는다.

`재시도: 불가`로 표시된 노드가 실패하면 `paseo run` 재호출은 0회다.

**기동 실패 재시도 금지 규칙과 사전에 계획된 품질 수정 루프는 다르다.** 앞은 위 표의
「재시도 금지」 열에 든 실패를 같은 조건으로 다시 띄우지 않는 규칙이고(「재시도 가능」 열의
기동 실패는 여기 해당하지 않는다), 뒤는 설계 때 검토 라운드 예산으로 미리 정해 둔 수정·재검토
반복이다. 품질 수정 루프는 이 절의 재시도 한도로 막히지 않는다. 다만 **권한 명시 거부**와
**수행 불가**(요청한 작업을 그 환경에서 끝낼 수 없음)는 품질 수정 루프로 우회할 수 없다 —
라운드를 더 줘도 같은 자리에서 막힌다. 그 둘은 노드를 `실패`로 두고 원인과 함께 사용자에게
보고한다.

**재수행 경로 갱신.** 실패 보고가 남은 노드를 같은 브리핑으로 재수행할 때는 재기동 **전에**
그 노드의 결과·실패 보고 경로를 `nodes/{노드 ID}-retry{N}.md`와
`nodes/{노드 ID}-retry{N}.failure.md`로 바꾸고, `GRAPH.md`의 해당 노드 **결과 칸**을 새 경로로
갱신한다. `{N}`은 재수행 횟수이며 검토 라운드 번호가 아니다. 앞 시도의 파일은 **지우거나
덮어쓰지 않는다** — 새 경로에 쓰므로 새 사용자 승인은 필요하지 않다.

판정은 **현재 시도**만 본다. `GRAPH.md` 결과 칸이 가리키는 **현재 시도의 결과 파일과 실패 보고
경로** 두 개가 유일한 **판정 근거**다. 현재 결과가 합격 기준을 충족하고 현재 실패 보고가 비어
있으면 `완료`이고, **앞 시도**의 실패 보고는 판정 근거가 아니다. 그것을 이유로 그 노드를 다시
띄우지 않는다.

## 불명 생성 — 중복 기동 금지

`paseo run` 호출이 타임아웃·전송 실패·출력 유실로 끝났고 `agentId`를 못 받았으면
**기동 실패로 단정하지 않는다.** 다시 띄우기 전에 조회한다.

1. 이 노드 행에 이미 `agentId`가 있으면 그 ID로 상태를 본다.
2. 없으면 `paseo ls -g --json --label run={실행 디렉터리 이름} --label node={노드 ID}`로
   실제 에이전트를 찾는다.
3. 에이전트가 있으면 그 `agentId`를 기록하고 중복 `paseo run`을 호출하지 않는다.
   실행 중이면 그대로 두고, 이미 끝났으면 「실패 보고 우선」으로 판정한다.
4. 조회가 `run`·`node` 라벨로 특정 에이전트를 확인했는데 결과가 비어 있어야 비로소
   기동 실패다. 그때만 위 「재시도」가 적용된다. 조회 자체가 실패했거나, 권한이 없어
   조회를 못 했거나, 여러 후보가 나와 특정하지 못하면 미생성 확인이 아니다. 다시
   띄우지 않는다.

## 실행 중 ID

노드 행에 `agentId`가 있으면 그 ID로 `paseo inspect <id> --json`을 부른다. **이 금지가
겨냥하는 것은 같은 노드를 실수로 두 번 띄우는 중복 기동이다** — 실행 중이거나 이미 합격
기준을 통과한 노드를 그것을 모른 채 완료 재기동하지 않는다. **의도한
재작업은 이 금지의 대상이 아니다** — 그때는 9절 「레벨 2 — 그래프 실행」의 재작업 절차를
따른다. ID를 버리고 그래프를 처음부터 다시 돌리지 않는다.

## 주입

실행 중인 워커에 지시를 보내는 수단은 `paseo send <id> <prompt>`다. 폐기할 때만
`paseo stop <id>`다. **호스트가 실행 중 메시지 또는 모드 변경을 막으면 보내지 않고
보고한다.**

- 조회형·범위 내 명확화는 승인 없이 보낸다. 이미 쓴 결과 파일을 덮어쓸지·이어 쓸지·버릴지를
  주입 프롬프트에 명시한다.
- 범위 변경(합격 기준 변경·추가, 대상 파일 추가, 역할 변경, 노드 추가·삭제, 되돌리기 어려운
  작업 추가, 권한을 올리는 모드 변경)은 **보내기 전에** 승인을 받는다. 승인 없이 종료하면
  호출하지 않고 `GRAPH.md`도 바꾸지 않는다.
- 레벨 2에서 범위 변경을 승인받으면 보낸 뒤 해당 노드 행을 `GRAPH.md`에 반영한다.
- 재설계(그래프 형태 변경, 토론 라운드 추가)는 9절의 계획 승인을 다시 받는다.
- 애매하면 범위 변경으로 본다.

사용자가 실행을 중단할 때 실행 중 전 노드를 중단하고, `GRAPH.md`를 그 시점 상태로 즉시
갱신한 뒤 노드별 상태와 남은 결과 파일 경로를 보고한다(9절 GRAPH.md).

## codex 셸 생성 실패

codex 워커의 실제 모드는 요청값과 다를 수 있고, 그 상태에서 `CreateProcessAsUserW` 오류로
셸이 뜨지 않은 사례가 있다. 상시 위험으로 관찰한다.

셸이 필요한 노드를 codex provider로 기동하면 기동 직후 `paseo inspect <id> --json`의 `Mode`를
읽는다. 이 노드는 모드가 실행 가능 여부를 가르므로 일괄 대조(4절)로 미루지 않는다.

**이 상태의 codex 워커는 쓰기는 되고 읽기가 안 된다.** `apply_patch`는 셸을 쓰지 않으므로
파일 생성·수정은 성공하지만, 파일 읽기는 셸에 의존하므로 실패한다. 결과는 "아무것도 못 하는
워커"가 아니라 **원본을 못 본 채 산출물을 지어내는 워커**이고, 파일이 실제로 생기기 때문에
파일 존재만으로는 이 실패가 드러나지 않는다.

- **원본 파일을 읽어야 하는 작업은 이 상태에서 codex 워커에 위임할 수 없다.** 셸 생성 실패가
  확인된 노드가 읽기를 필요로 하면 기동하지 않고, 읽기가 되는 워커로 배정하거나 사용자에게
  올린다.
- 그렇게 죽은 워커가 이미 낸 산출물은 합격 기준 대조 이전에 **폐기 대상**으로 본다. 읽지
  못한 원본을 근거로 썼을 수 있으므로 내용의 그럴듯함을 근거로 살리지 않는다.
- 합격 기준에 "원본의 어느 구간을 실제로 읽었는지"를 넣어 두면 이 실패가 판정에서 걸린다.

**`full-access`로 자동 승격하지 않는다.** 모드를 올리는 것은 권한 변경이고, 이 실패의 원인이
권한이 아닐 가능성이 높다 — 권한을 올려도 같은 자리에서 막히면서 승격만 남는다.

- 이 호스트가 그 모드를 막으면 바꾸지 않고 실패로 보고한다.
- 사용자가 그 노드에 이미 준 권한이 그 모드를 덮으면 재사용한다.
- 그 외에는 승인을 받은 뒤에만 재기동의 `--mode` 또는 호스트가 허용하는 실행 중 모드 변경으로
  바꾼다. 실행 중 메시지 자체가 호스트에 막혀 있으면 `paseo send`로 우회하지 않는다.
- 같은 값으로 재시도하지 않는다. 재기동이 허용된 경우에만 위 「재시도」 한도 1회에 센다.
  횟수는 호출 전에 기록한다.

codex라고 해서 특정 모드를 미리 강제하지 않는다.

## 쿼터 소진

제한 플랜에서 쿼터가 실행 도중에 마르면 남은 작업만 못 하는 것이 아니라 **이미 띄운 워커의
결과까지 못 받는다**(`research-orchestration` 1절). 그때까지 쓴 것이 통째로 버려지므로, 다른
실패와 달리 "일단 계속 돌려 보는" 선택지가 없다.

소진으로 판정하는 근거는 둘 중 하나다.

- 세션·사용량 한도 오류(한도 초과 문구, `429`)가 서로 다른 노드에서 반복된다.
- `research-orchestration` 1절에서 정한 이번 실행 총 워커 수 예산을 넘겨야 남은 작업을
  끝낼 수 있다.

판정하면 순서대로 한다.

1. **멈추는 것** — 대기 큐의 신규 기동을 전면 중단한다. 새 `paseo run`은 0회이고, 재시도
   한도가 남아 있어도 쓰지 않는다. 재시도도 쿼터를 쓴다.
2. **보존하는 것** — 실행 중인 워커는 중단하지 않고 결과를 받는다. 취소하면 그 워커에 이미
   쓴 쿼터가 회수되지 않고 버려진다. 결과를 받는 즉시 `GRAPH.md`의 상태와 결과 파일 경로를
   기록한다 — 기록이 남아야 쿼터 회복 뒤 아래 「재개」로 이어 갈 수 있다.
3. **아끼는 것** — 결과 파일 본문을 리더 컨텍스트로 옮기지 않는다. 판정에 필요한 범위만 읽고,
   취합을 위한 추가 워커를 띄우지 않는다.
4. **알리는 것** — 소진을 판정한 근거(오류 원문 한 줄 또는 넘긴 예산 값), 이미 받은 결과 파일
   경로, 결과를 기다리는 실행 중 노드, 미기동으로 남은 노드 수, 그리고 `GRAPH.md` 경로를
   낸다. 이어 가려면 무엇이 필요한지를 함께 적는다.
5. **사용자 결정을 받는다** — 남은 작업을 합칠지, 다음 실행으로 미룰지, 예산을 늘릴지는
   `research-orchestration` 1절의 세 선택지 그대로다. **임의로 작업을 빼고 완료로 보고하지
   않는다.**

**대체 provider로 폴백하지 않는다.** 이 플러그인은 codex 단독 환경을 전제하므로 갈아탈
provider가 없고, 쿼터는 provider를 바꾼다고 회복되지 않는다. 리더가 워커 대신 남은 작업을
직접 수행하지도 않는다 — 그것은 위임 게이트를 우회하는 것이고, 리더의 컨텍스트도 같은 쿼터를
쓴다.

## 재개

중단·압축 복구는 레벨 1·2가 같은 절차를 쓴다 — 레벨 1의 서술은 3절 「레벨 1 재개」이고
동작이 이 절과 같다. 다만 7·8은 레벨 2에만 해당한다 — 레벨 1에는 스테이지가 없고
재사용할 계획 승인도 없다. 같은 요청의 중단·압축 복구에 쓴다. 새 요청의 그래프를
재사용하는 경로가 아니다.

1. `paseo ls -g --json --label run={실행 디렉터리 이름}`으로 자식 에이전트를 조회한다.
   `run` 라벨은 기동할 때 붙인 값이다(4절). 무엇이 이미 떠 있는지 확인한 뒤에 설계로
   돌아갈지 판단한다.
2. 실행 디렉터리의 `GRAPH.md`가 있으면 읽는다. 기록 파일이 없고 자식도 없으면 재개가
   아니라 설계다 — 레벨 2는 9절, 레벨 1은 2절 레벨 판정부터다.
3. `agentId`가 있는 행마다(또는 조회된 자식마다) 먼저 실제 에이전트가 실행 중인지
   조회한다. **실행 중이면** 실패 보고 경로에 내용이 있어도 중복 기동하지 않고 상태를
   `실행 중`으로 맞춘 채 종료를 기다린다. `완료`이거나 실행 중인 노드는 다시 띄우지
   않는다.
4. 종료가 확인된 뒤에 결과 파일 경로와 **실패 보고 경로**를 대조해 「실패 보고 우선」 순서로
   판정한다.
5. `GRAPH.md`가 `완료`로 기록돼 있다는 것만으로 완료 처리하지 않는다. 위 조회·대조 결과가
   그 기록과 다르면 재실행하지 않고 불일치를 보고한 뒤 그 노드에 의존하는 노드는
   기동하지 않는다.
6. `대기`는 기동한다. `실패` 노드는 재시도 조건과 잔여 횟수를 충족할 때만 재기동한다.
   한도를 이미 썼으면 기동하지 않고 보고한다. 명시 거부된 노드는 기동하지 않는다.
7. 스테이지를 반만 채운 채 다음으로 넘기지 않는다. 선택된 경로의 활성 노드가 통과하고 필요한
   사용자 게이트가 확정되면 다음 스테이지로 간다. `생략`은 차단 원인이 아니다.
8. 그래프 형태가 그대로면 이미 받은 계획 승인을 재사용한다.

기록이 실행 중인데 에이전트가 없고 합격 기준을 통과한 결과 파일도 없으면 「불명 생성」으로
조회한 뒤 `실패` 또는 확인된 미생성으로 맞춘다. 추측으로 완료 재기동하지 않는다.

앞 실행이 쿼터 소진으로 멈춘 것이면 재개 전에 이번 실행의 예산을 다시 정한다 —
`research-orchestration` 1절이 그 값을 공급한다. 예산을 정하지 않은 채 남은 `대기` 노드를
한꺼번에 기동하면 같은 자리에서 다시 마른다.
