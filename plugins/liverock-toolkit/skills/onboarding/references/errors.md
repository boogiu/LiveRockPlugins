# 오류 메시지 사전

점검 중 실패가 났을 때, 또는 사용자가 오류 메시지를 들고 왔을 때 여는 표다.

이 플러그인을 쓰는 사람은 codex·claude CLI를 모른다. 원문 메시지는 그에게 아무 정보가
아니므로, **뜻과 조치를 먼저 말하고 원문은 뒤에 붙인다.**

여기 적힌 메시지는 이 환경에서 **실제로 관찰된 것만**이다. 표에 없는 메시지가 나오면
비슷한 항목에 억지로 맞추지 않는다. 아래 「표에 없는 메시지」를 따른다.

## 표

| 실제 메시지 | 뜻 | 조치 | 담당 |
| --- | --- | --- | --- |
| `Not logged in` (`codex login status`의 출력) | **codex에 로그인이 돼 있지 않다.** 점검 10번이 이 줄로 실패를 낸다. 로그인된 환경에서는 같은 자리에 `Logged in using ChatGPT`가 나온다. **종료코드로는 갈리지 않는다** — 두 경우 모두 0이 관찰됐으므로 종료코드만 보면 로그인 안 된 환경도 통과로 나온다 | 사용자가 `codex login`으로 로그인한다. **에이전트가 대신 로그인하지 않는다** — 자격 증명이고 브라우저 상호작용이 필요하다. 이 상태에서는 codex 자체를 못 쓰므로 나머지 점검을 진행하지 말고 **확인 불가**로 적는다. 여기서 1번을 "플러그인이 없다"로 적으면 사용자가 설치를 다시 시도하다가 진짜 원인을 지나친다 | 에이전트가 확인, 로그인은 **사용자** |
| `error: unknown command 'profile'` / `(Did you mean provider?)` (`paseo profile` 실행) | **`paseo`에는 프로필을 조회하는 명령이 없다.** 점검 7번(프로필 등록)을 CLI로 보려다 나온다. 명령을 잘못 친 것이 아니라 그런 명령이 애초에 없다 | 다른 이름을 찾아 헤매지 않는다. 7번은 `profile-setup` 스킬에 넘겨 등록된 목록을 받아 판정한다. 목록을 못 받았으면 통과가 아니라 **확인 불가**다 | 에이전트 |
| `CreateProcessAsUserW failed: -1073283067 (Win32 error -1073283067)` | 워커를 띄우려는데 **프로그램 실행 자체가 이 PC에서 막혔다.** 권한이 모자라서가 아니라 실행 환경 쪽 문제다. 이 상태의 codex 워커는 **파일 쓰기는 되는데 읽기가 안 된다** — 그래서 "아무것도 못 하는 워커"가 아니라 원본을 못 본 채 그럴듯한 파일을 만들어 내는 워커가 된다 | 원본 파일을 읽어야 하는 작업은 이 워커에 맡기지 않는다. 그 워커가 이미 낸 산출물은 내용이 그럴듯해도 폐기 대상으로 본다. **권한 모드를 올려 우회하지 않는다** — 원인이 권한이 아니라서 모드만 올라가고 같은 자리에서 다시 막힌다. 같은 값으로 다시 띄우지 않는다 | 에이전트가 판정하고, 모드 변경이나 재기동은 **사용자** 승인을 받는다 |
| `'codex'은(는) 내부 또는 외부 명령, 실행할 수 있는 프로그램, 또는 배치 파일이 아닙니다.` | **`codex`라는 이름의 프로그램을 찾지 못했다.** 둘 중 하나다 — 설치가 안 됐거나, 설치는 됐는데 그 위치를 시스템이 찾는 경로 목록(PATH)에 넣어 두지 않았다. Windows에서 특히 자주 생기는 이유가 있다: npm으로 전역 설치하면 `codex`(확장자 없음)·`codex.cmd`·`codex.ps1` 세 파일이 함께 깔리는데, **확장자 없는 쪽을 잡으면 Windows가 그것을 실행하지 못한다.** 설치돼 있는데도 없는 것처럼 보이는 상태다 | 점검 9번의 실패 시 조치를 따른다. 실행 파일의 **실제 경로**를 찾아 사용자에게 보여 주고, 그 값을 Paseo 설정에 넣게 한다. 경로를 찾지 못했으면 어디를 찾아봤는지까지 함께 전한다 | 에이전트가 경로를 찾아 제시하고, 설정 반영과 설치는 **사용자** |
| `paseo provider ls --json`의 `status`가 `available`이 아니다 (관찰된 값: `available` / `unavailable`). 같은 상태를 `paseo status`는 Providers 절에 `not found (daemon)`으로 낸다 | **Paseo 데몬은 정상인데, 그 provider를 실행할 프로그램을 데몬이 못 찾은 상태다.** 이대로 워커를 띄우면(`paseo run`) 실패하는데, 화면에는 무엇이 없어서 실패했는지 안 나온다 | 점검 9번을 본다. `paseo provider diagnostic <provider> --json`으로 실행 파일의 실제 경로를 찾아 제시하고, 사용자가 Paseo 설정에 반영한 뒤 다시 조회해 `available`이 되는지 확인한다 | 에이전트가 조회·제시, 설정 반영은 **사용자** |
| 오류 화면이 가리킨 `...\Codex\bin\<16자리 hex>\codex-code-mode-host.exe`가 없다는 메시지 | **Codex CLI가 띄우는 자식 프로세스인 `codex-code-mode-host.exe`의 그 경로에 실물 파일이 없다.** 이는 아래 Paseo provider 오류와 별개의 계층이다. 먼저 `Get-Process codex,codex-code-mode-host,Paseo -ErrorAction SilentlyContinue \| Select-Object ProcessName,Path`를 실행한다. 출력 경로는 현재 실행 중인 프로세스의 실제 파일이고, 출력이 없으면 그 프로세스가 현재는 실행 중이지 않다는 뜻이다 | 오류에 나온 전체 경로를 그대로 넣어 `Test-Path -LiteralPath '<오류에 뜬 전체 경로>'`를 실행한다. `True`면 파일은 현재 존재하므로 Codex·ChatGPT·Paseo를 모두 종료했다가 다시 열어 재현 여부와 위 프로세스 경로를 기록한다. `False`면 재시작만으로 사라진 파일이 복구되지는 않는다. 오류 전문·발생 시각·직전 업데이트 시각과 위 출력, 상위 `bin`의 하위 폴더 목록을 보존하고, 사용자 승인 후 현재 설치한 Codex/ChatGPT 앱의 정식 업데이트·복구 또는 재설치를 한 뒤 같은 `Test-Path`로 복구를 확인한다. 파일을 다른 위치에서 복사하거나 빈 파일로 만들지 않는다. 해시 폴더 이름의 결정 방식, 세션이 경로를 고정하는지, 업데이트가 옛 폴더를 지우는지는 아직 확인되지 않았으므로 원인으로 단정하지 않는다 | 에이전트가 점검·기록, 앱 복구 또는 재설치는 **사용자** |
| `Provider 'codex' is not available. Please ensure the CLI is installed.` | **Paseo가 기존 세션을 다시 열 때 Codex CLI를 실행 가능하다고 판정하지 못했다.** 누락된 host 파일을 직접 검사한 메시지는 아니다. Paseo는 PATH·WinGet·Windows Store 후보와 provider의 command override를 대상으로 `codex --version` 실행 가능성을 확인한다. 이 플러그인의 0.3.0부터 워커는 `paseo run`으로 기동하므로, 워커를 띄우려면 이 판정이 통과해야 한다. 다만 0.3.0이 이 오류를 일으켰다는 인과는 확인되지 않았다 | `Get-Command codex -All \| Select-Object Name,Source`를 실행한다. 출력이 없으면 PATH에서 CLI를 못 찾은 것이므로 설치 위치를 확인해 Paseo의 provider `codex` command override에 실제 실행 파일을 지정하거나 사용자에게 CLI 설치·복구를 요청한다. 출력이 있으면 이어서 `codex --version`을 실행한다. 버전이 나오면 현재 셸의 CLI는 실행 가능하므로 Paseo의 `codex` provider override가 다른 경로를 가리키는지 확인하고, 실제 실행 파일로 고친 뒤 provider 상태를 다시 조회한다. 버전 실행이 실패하면 그 오류를 기준으로 CLI 설치·PATH·실행 권한을 복구한 뒤 두 명령을 다시 실행한다 | 에이전트가 점검·경로 제시, 설정 반영과 설치·복구는 **사용자** |
| `ModuleNotFoundError: No module named 'yaml'` | 파이썬 스크립트가 **이 PC의 파이썬에 없는 부품을 쓰려다 멈췄다.** 코드가 틀린 게 아니라 준비물이 빠진 것이다 | 어느 스크립트가 낸 것인지 먼저 가린다. 이 플러그인의 스크립트는 표준 라이브러리만 쓰므로 여기서 이 메시지가 나오면 결함이니 그 사실을 보고한다. 플러그인 밖 스크립트면 패키지 설치가 필요한데, 설치는 사용자 환경 변경이라 방법만 제시하고 멈춘다 | 에이전트가 원인을 가리고, 설치는 **사용자** |

## 표에 없는 메시지

추측으로 뜻을 붙이지 않는다. 틀린 해석은 없는 것보다 나쁘다 — 사용자가 그 설명을 믿고
엉뚱한 곳을 고치다가 진짜 원인을 지나친다.

1. 원문을 **그대로** 사용자에게 전한다. 요약하거나 다듬지 않는다.
2. "이 메시지는 아직 확인된 사례가 없다"고 밝힌다.
3. 대신 **어느 점검 항목에서 났는지**를 알린다. 그것이 사용자가 다음에 볼 자리다.
