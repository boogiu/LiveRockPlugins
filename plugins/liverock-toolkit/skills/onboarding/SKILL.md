# 환경 점검과 초기 구성

이 플러그인을 처음 받은 사람은 codex와 Paseo 설정에 익숙하지 않다. 그래서 목표는
"점검을 돌렸다"가 아니라 **아홉 항목이 전부 판정된 표 하나와, 사용자가 지금 할 일 하나**를
내놓는 것이다.

## 맡는 것과 맡지 않는 것

| 축 | 담당 |
| --- | --- |
| 처음 한 번 환경 전체를 갖추는 것 | 이 스킬 |
| 워커 하나를 띄우기 직전의 연결·워크스페이스 확인 | `agent-orchestration` 1절 「전제 점검」 |
| 프로필을 설계·등록·변경·삭제하는 절차 | `profile-setup` |

`agent-orchestration` 1절과 이 스킬의 4·5·6번은 같은 대상(MCP 연결, 워크스페이스)을 본다.
겹치는 것은 확인 대상이지 역할이 아니다. **이 스킬은 그 전제를 처음에 한 번 갖춰 놓고,
`agent-orchestration`은 기동 직전마다 지금 이 순간의 상태를 다시 본다.** 여기서 통과했다고
그쪽 점검을 건너뛰지 않는다 — 설정은 세션 사이에 바뀌고, 앱이 내려가 있을 수도 있다.
반대로 그쪽 점검이 막혀 기동을 못 하면 원인이 환경 전제이므로 이 스킬로 돌아온다.

## 판정은 세 가지다

각 항목을 **통과 / 실패 / 확인 불가**로 적는다. 셋을 둘로 줄이지 않는다.

| 판정 | 뜻 |
| --- | --- |
| 통과 | 확인했고 기준을 만족했다 |
| 실패 | 확인했고 기준을 만족하지 못했다 |
| 확인 불가 | 확인 자체를 못 했다. 앞 항목이 막혔거나 조회 수단이 없다 |

**확인 못 한 것을 통과로 적지 않는다.** 빈칸과 「확인 불가」는 다음에 볼 자리를 남기지만,
잘못 채워진 통과는 아무 신호도 남기지 않아서 나중에 워커가 안 뜰 때 원인을 여기서 찾지
못한다. 애매하면 「확인 불가」 쪽으로 적는다.

## 권한 경계

**저장소 밖 설정과 앱 설치는 에이전트가 직접 하지 않는다.** 사용자 전역 설정을 에이전트가
고치면 사용자가 모르는 사이에 이 저장소 밖의 다른 작업 환경까지 바뀐다. 그쪽은 구체적인
방법을 제시하고 멈춘다.

| 구분 | 해당 항목 | 동작 |
| --- | --- | --- |
| 조회만 | 1·2·3·6·9 | 승인 없이 확인한다. 상태를 바꾸지 않는다 |
| 에이전트가 실행 | 7·8 | **무엇을 할지 먼저 보이고 답을 받은 뒤** 직접 실행한다 |
| 사용자에게 넘김 | 4·5, 9번의 설정 반영 | 구체적인 방법을 제시하고 멈춘다. 에이전트가 고치지 않는다 |

## 순서

앞이 막히면 뒤를 확인할 수 없는 관계가 있다. **4·5가 실패하면 9와 6·7은 MCP 조회 자체가
안 되므로 확인 불가로 적는다.** 여기서 6·7을 통과로 적으면 사용자는 프로필이 있다고 믿고
작업을 시작했다가 워커가 안 뜨는 이유를 못 찾는다.

**9번은 7번보다 먼저 본다.** 프로필은 provider를 가리키는 값이므로, provider를 실행할
프로그램이 없으면 프로필이 등록돼 있어도 워커가 안 뜬다. 순서를 뒤집으면 "프로필 통과"만
보고 원인을 프로필 쪽에서 찾게 된다.

```text
1·2·3·8  (스크립트 한 번)  →  4·5  (사용자)  →  9  (provider)  →  6·7  (MCP 조회)
                                  실패 시 ─────→  9·6·7 = 확인 불가
```

## 1단계 — 1·2·3·8을 스크립트로 한 번에

```text
python scripts/check_env.py
```

표로 돌려준다. 결과를 다음 단계에 값으로 넘겨야 하면 `--json`을 붙인다.
`--network-timeout`은 기본 5초이고, 느린 사내망이면 올린다. 저장소 밖에서 실행해
루트를 못 찾으면 `--repo-root`로 준다.

이 스크립트는 상태를 바꾸지 않는다. 8번 디렉터리도 **만들지 않고 만들 수 있는지만** 본다.

| # | 항목 | 확인 방법 | 통과 기준 | 실패 시 조치 | 담당 |
| --- | --- | --- | --- | --- | --- |
| 1 | 플러그인 설치·활성 | `codex plugin list` | 출력에 `liverock-toolkit@liverock`이 있고 `installed, enabled` | `codex plugin add liverock-toolkit@liverock`을 사용자에게 제시한다. 설치 절차는 저장소 `README.md`에 있고 여기서 다시 쓰지 않는다 | 에이전트 |
| 2 | Python 3 | `python --version` | 메이저 버전 3 이상 | Python 3 설치를 안내하고 멈춘다. 설치는 사용자 환경 변경이라 에이전트가 하지 않는다 | 에이전트 |
| 3 | 네트워크 | OpenAlex 공개 엔드포인트에 짧은 타임아웃으로 한 번 요청 | 응답이 온다(HTTP 상태는 무관 — 도달 여부만 본다) | 프록시·방화벽을 사용자에게 알린다. 막혀 있으면 논문 탐색이 안 되므로 `literature-analysis`를 쓸 수 없다고 명시한다 | 에이전트 |

스크립트가 `확인 불가`를 내면 그대로 표에 옮긴다. stderr 진단에 원인이 한 줄로 남아 있으니
그 줄도 사용자에게 전하되, **아래 「오류를 전하는 순서」를 지킨다.**

표 아래에 나오는 `provider CLI 실행 경로` 절은 9번에서 쓴다. 여기서는 판정하지 않고
값만 들고 간다.

## 오류를 전하는 순서

**뜻과 조치를 먼저 말하고, 원문은 그 뒤에 붙인다.** 원문을 지우지는 않는다.

```text
(1) 이게 무슨 뜻인지  →  (2) 지금 무엇을 하면 되는지  →  (3) 원문 메시지
```

이 순서인 이유는 **읽는 사람이 codex·claude CLI를 모르기 때문이다.** `CreateProcessAsUserW
failed: -1073283067`을 먼저 던지면 사용자는 뜻을 모른 채 자기가 뭘 잘못했다고 생각하고
멈춘다. 반대로 원문을 빼 버리면 나중에 검색하거나 다른 사람에게 물을 때 쓸 것이 없어진다.
그래서 **지우는 게 아니라 순서만 뒤집는다.** 규칙의 목적이 "원문 감추기"가 아니라 "먼저
읽을 것을 앞에 두기"이므로, 사용자가 원문을 직접 들고 와서 묻는 경우에도 답은 뜻과 조치가
먼저다.

뜻과 조치는 [`references/errors.md`](references/errors.md)에 정리돼 있다. **점검 중 실패가
나왔을 때, 또는 사용자가 오류 메시지를 들고 왔을 때만 연다.** 평소에는 읽지 않는다.
거기 없는 메시지는 뜻을 지어내지 말고 그 파일의 「표에 없는 메시지」를 따른다.

## 2단계 — 4·5는 사용자가 한다

여기가 이 스킬이 있는 가장 큰 이유다. **`daemon.mcp.injectIntoAgents`는 기본값이 `false`다.**
꺼져 있으면 Paseo MCP 도구가 새 세션에 주입되지 않아 워커를 아예 못 띄우는데, 화면에는
"도구가 없다"는 말조차 안 나오고 그냥 안 된다. 그래서 **9와 6·7로 넘어가기 전에 4·5를 반드시
확인시킨다.** 1·2·3·8을 스크립트로 먼저 돌리는 것은 그것이 빠르고 사용자 손을 안 빌리기
때문이지, 4·5가 덜 중요해서가 아니다.

| # | 항목 | 확인 방법 | 통과 기준 | 실패 시 조치 | 담당 |
| --- | --- | --- | --- | --- | --- |
| 4 | Paseo 앱 | 이 세션에 Paseo MCP 도구(`list_workspaces`, `list_profiles`, `create_agent` 등)가 붙어 있는지 본다 | 도구가 이 세션에서 호출 가능하다 | Paseo 앱을 설치·실행하라고 알리고 멈춘다. 앱 설치는 에이전트가 하지 않는다 | **사용자** |
| 5 | MCP 도구 주입 | 4번이 실패했고 앱은 떠 있다면 `daemon.mcp.injectIntoAgents` 설정을 의심한다 | 값이 활성(`true`)이고 그 뒤 새로 연 세션에 도구가 붙는다 | 아래 방법을 제시하고 멈춘다 | **사용자** |

5번이 실패일 때 사용자에게 전할 것:

1. Paseo 설정에서 `daemon.mcp.injectIntoAgents`를 `true`로 바꾼다 — 앱 설정 화면의 MCP
   항목이든 설정 파일이든 사용자가 쓰는 쪽에서 한다.
2. 데몬을 재시작한다.
3. **세션을 새로 연다.** 주입은 세션이 뜰 때 일어나므로, 값만 바꾸고 지금 세션을 그대로
   쓰면 도구가 여전히 없다. 여기서 막히는 경우가 대부분이다.

**에이전트가 이 값을 직접 고치지 않는다.** 사용자 전역 설정이고, 이 저장소 밖의 다른
작업까지 영향을 받는다. 바꿨다는 답을 받은 뒤 새 세션에서 4번부터 다시 본다.

## 3단계 — 9는 provider가 실제로 실행되는지 본다

4·5가 통과했을 때만 여기로 온다. **앱이 정상이고 MCP 도구도 붙었는데 provider CLI 실행
파일만 못 찾는 상태**가 여기서 걸린다. 이때 `create_agent`가 실패하는데 사용자는 무엇이
없어서 실패했는지 알 수 없다.

| # | 항목 | 확인 방법 | 통과 기준 | 실패 시 조치 | 담당 |
| --- | --- | --- | --- | --- | --- |
| 9 | provider 실행 경로 | `list_providers`로 각 provider의 `status`를 본다 | 쓰려는 provider의 `status`가 `available`이다 | 1단계 스크립트 출력의 `provider CLI 실행 경로` 절에서 **실제 실행 파일 경로**를 찾아 사용자에게 그대로 보여 주고, 그 값을 Paseo 설정의 해당 provider 실행 경로에 넣으라고 안내한다. 경로를 못 찾았으면 스크립트가 **찾아본 위치 목록**을 냈으니 그것을 전한다 | 에이전트가 경로를 찾아 제시하고, **설정 반영은 사용자** |

**"못 찾았다"로 끝내지 않는다.** 이 항목의 목적은 판정이 아니라 **사용자가 Paseo 설정에
넣을 값을 손에 쥐여 주는 것**이다. 경로를 직접 찾아 헤매게 만들면 여기서 온보딩이 멈춘다.

1단계를 건너뛰고 들어왔거나 그때 경로를 못 받았으면 스크립트를 다시 돌린다.

```text
python scripts/check_env.py
```

Windows에서 npm으로 깐 경우 `codex`(확장자 없음)·`codex.cmd`·`codex.ps1`이 함께 깔린다.
**확장자 없는 쪽을 설정에 넣으면 실행되지 않는다.** 스크립트는 실행 가능한 쪽을 골라서
내므로, 스크립트가 낸 경로를 그대로 쓰게 한다.

`status`가 `available`이 아닌 provider를 프로필이 가리키고 있으면 그 프로필은 쓸 수 없다.
9번이 실패면 7번은 **확인 불가**로 적는다 — 프로필이 등록돼 있어도 그 워커는 안 뜬다.

## 4단계 — 6·7은 MCP로 조회한다

4·5·9가 통과했을 때만 여기로 온다. 하나라도 실패·확인 불가면 6·7을 **확인 불가**로 적고
앞 단계 결과와 함께 보고한 뒤 멈춘다.

| # | 항목 | 확인 방법 | 통과 기준 | 실패 시 조치 | 담당 |
| --- | --- | --- | --- | --- | --- |
| 6 | 워크스페이스 | `list_workspaces` | `cwd`가 사용자의 연구 디렉터리인 워크스페이스가 하나 이상 있다 | 어느 디렉터리를 쓸지 사용자에게 묻고, 답을 받은 뒤 만든다. 어느 경로인지 모르는 채로 만들지 않는다 | 에이전트 |
| 7 | 프로필 등록 | `list_profiles` | 결과가 비어 있지 않다 | `profile-setup`으로 넘긴다 (아래) | 에이전트 |

6번은 조회만 하는 항목이다. 워크스페이스를 새로 만드는 것은 조회가 아니므로, 대상 경로를
사용자에게 확인받은 뒤에 한다. 워크스페이스를 생략하고 워커를 띄우면 엉뚱한 새
워크스페이스가 생기므로, 여기서 경로를 못 정했으면 확인 불가로 남긴다.

### 7번이 실패면

`list_profiles`가 비어 있으면 팀장 에이전트가 위임할 곳을 고를 근거가 없어서 워커를
띄워도 라우팅이 성립하지 않는다. **`profile-setup` 스킬로 넘긴다.**

사용자에게 알릴 것은 두 가지뿐이다.

- `profile-setup`이 저가형·고가형 두 프리셋 세트를 가지고 있다.
- 기본 제안은 저가형이다.

**등록 절차 자체를 여기에 옮겨 적지 않는다.** provider 조회, 모델 선택, mode 확인, 설정
반영 순서는 전부 `profile-setup`에 있다. 같은 절차가 두 벌이면 한쪽만 고쳐졌을 때 어느
쪽이 맞는지 알 수 없고, 고칠 곳이 두 군데가 된다. 등록이 끝나면 이 스킬로 돌아와 7번을
다시 조회해 판정한다.

## 5단계 — 보고

아홉 항목을 **한 표로** 낸다. 통과한 것만 추리거나 실패한 것만 내지 않는다 — 사용자가
알아야 하는 것은 "무엇이 남았나"이고, 그건 전체를 봐야 보인다.

```text
| # | 항목 | 판정 | 근거 | 다음 동작 |
```

표 아래에 **지금 사용자가 할 일 하나**를 적는다. 여러 개가 남았으면 순서상 가장 앞의 것
하나만 적는다. 익숙하지 않은 사용자에게 할 일 다섯 개를 한꺼번에 주면 어디서부터 손댈지
모른 채 멈춘다.

전부 통과했으면 그 사실을 적고, 바로 쓸 수 있는 스킬을 한 줄로 안내한다 — 논문은
`literature-analysis`, 실험 계획은 `experiment-planning`, 여러 작업을 나눠 돌리는 것은
`research-orchestration`과 `agent-orchestration`.

## 막혀서 들어온 경우

다른 스킬이 진행하지 못해 이쪽으로 왔으면 아홉 항목을 처음부터 다 돌린다. 증상만 보고
한 항목을 찍어 고치면 그 앞의 원인이 남아 같은 자리에서 다시 막힌다.

| 증상 | 먼저 볼 항목 |
| --- | --- |
| 워커가 안 뜬다, MCP 도구가 없다고 한다 | 4 → 5 |
| 도구는 있는데 워커 생성만 실패한다, provider가 `unavailable`이다 | 9 |
| 워커는 뜨는데 엉뚱한 디렉터리에서 돈다 | 6 |
| 위임할 프로필을 못 고른다 | 7 |
| 논문 검색이 실패한다 | 3 → 2 |
| 스킬이 아예 발동하지 않는다 | 1 |
| 실행 기록이 안 남거나 git에 잡힌다 | 8 |

이 표는 어디부터 볼지를 정할 뿐이고, 판정은 아홉 항목 전부에 대해 적는다.

사용자가 오류 메시지를 들고 왔으면 그것부터 위 「오류를 전하는 순서」로 풀어 준 뒤 점검에
들어간다. 뜻을 모르는 채로 점검 아홉 개를 시작하면 사용자는 자기 질문이 무시됐다고 본다.
