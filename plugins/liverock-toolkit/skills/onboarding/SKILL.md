# 환경 점검과 초기 구성

이 플러그인을 처음 받은 사람은 codex·Claude Code와 Paseo 설정에 익숙하지 않다. 그래서 목표는
"점검을 돌렸다"가 아니라 **현재 호스트에 해당하는 항목이 전부 판정된 표 하나와, 사용자가 지금 할 일 하나**를
내놓는 것이다.

## 먼저 호스트를 구분한다

현재 세션이 codex인지 Claude Code인지 먼저 확인한다. `scripts/check_env.py`는 Claude Code 환경을
감지하면 Claude 항목만, 그 밖에는 기존 codex 항목만 점검한다. 자동 감지가 애매하거나 두 설치본을
모두 확인해야 하면 각각 `--host codex`, `--host claude`, `--host both`를 붙인다.

Claude Code에서 **10번 codex 로그인은 실패가 아니라 해당 없음**이다. Claude 항목으로 바꾸어
점검하며, codex 설치본도 함께 쓸 때만 `--host both`로 codex 로그인·플러그인 항목을 추가한다.

## 맡는 것과 맡지 않는 것

| 축 | 담당 |
| --- | --- |
| 처음 한 번 환경 전체를 갖추는 것 | 이 스킬 |
| 워커 하나를 띄우기 직전의 연결·워크스페이스 확인 | `agent-orchestration` 1절 「전제 점검」 |
| 프로필을 설계·등록·변경·삭제하는 절차 | `profile-setup` |

`agent-orchestration` 1절과 이 스킬의 4·5·6번은 같은 대상(Paseo 데몬 연결, 워크스페이스)을 본다.
겹치는 것은 확인 대상이지 역할이 아니다. **이 스킬은 그 전제를 처음에 한 번 갖춰 놓고,
`agent-orchestration`은 기동 직전마다 지금 이 순간의 상태를 다시 본다.** 여기서 통과했다고
그쪽 점검을 건너뛰지 않는다 — 설정은 세션 사이에 바뀌고, 앱이 내려가 있을 수도 있다.
반대로 그쪽 점검이 막혀 기동을 못 하면 원인이 환경 전제이므로 이 스킬로 돌아온다.

## 판정은 세 가지다

각 항목을 **통과 / 실패 / 확인 불가**로 적는다. 셋을 둘로 줄이지 않는다.

| 판정 | 뜻 |
| --- | --- |
| 통과 | 확인했고 기준을 만족했다 |
| 실패 | 확인했고 기준을 만족하지 못했다 |
| 확인 불가 | 확인 자체를 못 했다. 앞 항목이 막혔거나 조회 수단이 없다 |

**확인 못 한 것을 통과로 적지 않는다.** 빈칸과 「확인 불가」는 다음에 볼 자리를 남기지만,
잘못 채워진 통과는 아무 신호도 남기지 않아서 나중에 워커가 안 뜰 때 원인을 여기서 찾지
못한다. 애매하면 「확인 불가」 쪽으로 적는다.

## 권한 경계

**저장소 밖 설정과 앱 설치는 에이전트가 직접 하지 않는다.** 사용자 전역 설정을 에이전트가
고치면 사용자가 모르는 사이에 이 저장소 밖의 다른 작업 환경까지 바뀐다. 그쪽은 구체적인
방법을 제시하고 멈춘다.

| 구분 | 해당 항목 | 동작 |
| --- | --- | --- |
| 조회만 | 10·1·2·3·4·5·6·9 | 승인 없이 확인한다. 상태를 바꾸지 않는다 |
| 에이전트가 실행 | 7·8 | **무엇을 할지 먼저 보이고 답을 받은 뒤** 직접 실행한다 |
| 사용자에게 넘김 | 4번의 앱 설치·실행, 5번의 데몬 재시작, 10번의 로그인, 9번의 설정 반영 | 구체적인 방법을 제시하고 멈춘다. 에이전트가 고치지 않는다 |

## 순서

앞이 막히면 뒤를 확인할 수 없는 관계가 있다. **4·5가 실패하면 9와 6은 Paseo 데몬에 물을
수단 자체가 없고 7도 근거가 없으므로 확인 불가로 적는다.** 여기서 6·7을 통과로 적으면
사용자는 프로필이 있다고 믿고 작업을 시작했다가 워커가 안 뜨는 이유를 못 찾는다.

**codex에서는 10번이 1번보다 앞이다.** 로그인이 안 돼 있으면 codex 자체를 쓸 수 없고, 1번(플러그인
설치·활성)은 이미 로그인된 상태를 전제한다. 10번이 실패면 로그인 방법을 안내하고 멈춘 뒤
나머지를 **확인 불가**로 적는다. 여기서 1번을 "플러그인이 없다"로 적으면 사용자는 설치를
다시 시도하다가 진짜 원인인 로그인을 지나친다.

**9번은 7번보다 먼저 본다.** 프로필은 provider를 가리키는 값이므로, provider를 실행할
프로그램이 없으면 프로필이 등록돼 있어도 워커가 안 뜬다. 순서를 뒤집으면 "프로필 통과"만
보고 원인을 프로필 쪽에서 찾게 된다.

```text
codex:  10  (로그인)  →  1·2·3·8  (스크립트 한 번)  →  4·5  (paseo CLI)  →  9  (provider)  →  6·7  (워크스페이스·프로필)
claude:      1·2·3·8  (스크립트 한 번)  →  4·5  (paseo CLI)  →  9  (provider)  →  6·7  (워크스페이스·프로필)

10 실패   →  1 이후 전부 확인 불가
4·5 실패  →  9·6·7 확인 불가
```

## 0단계 — codex를 처음 켤 때 만나는 것

**점검 항목이 아니라 안내다.** 연구원이 codex를 처음 실행하면 이 플러그인에 닿기 전에
확인 화면 넷을 지난다. 무엇을 묻는 화면인지 모르면 여기서 멈춘다.

| 순서 | 화면 | 나오는 선택지 | 무엇을 고르나 |
| --- | --- | --- | --- |
| 1 | 로그인 | `1. Sign in with ChatGPT` / `2. Sign in with Device Code` / `3. Provide your own API key` | 쓰는 계정에 맞는 것을 **사용자가** 고른다. 자격 증명이고 브라우저 상호작용이 필요하므로 에이전트가 대신 하지 않는다 |
| 2 | 업데이트 안내 | `Update available! 0.155.0 -> 0.155.1` / `1. Update now` / `2. Skip` / `3. Skip until next version` | **건너뛴다.** 온보딩 도중에 업데이트하면 환경이 바뀌어 점검 결과가 흔들린다. 버전 숫자는 환경마다 다르다 |
| 3 | 디렉터리 신뢰 | `Do you trust the contents of this directory?` / `1. Yes, continue` / `2. No, quit` | **사용자가 판단한다.** 에이전트가 "예"를 권하지 않는다 |
| 4 | 샌드박스 설정 | `1. Set up default sandbox (requires Administrator permissions)` / `2. Use non-admin sandbox (higher risk if prompt injected)` / `3. Quit` | 아래를 읽고 **사용자가 고른다** |

### 샌드박스는 사용자가 고른다

**1번 선택지가 관리자 권한을 요구한다.** 에이전트는 권한 상승을 권하지 않는다. 두 선택지의
차이만 전하고 고르는 것은 사용자에게 맡긴다.

| 선택지 | 뜻 |
| --- | --- |
| `1. Set up default sandbox` | codex가 기본 샌드박스를 구성한다. 화면이 밝히는 대로 **관리자 권한이 필요하다** |
| `2. Use non-admin sandbox` | 관리자 권한 없이 진행한다. 화면이 밝히는 대로 `higher risk if prompt injected`이고, 명령마다 승인을 묻는다 |

**비관리자 샌드박스를 골라도 이 플러그인은 동작한다.** 이 온보딩을 비관리자 샌드박스에서
끝까지 돌려 확인했다.

### 승인 프롬프트가 여러 번 뜬다 — 점검 전에 미리 알린다

비관리자 샌드박스를 고르면 **명령마다 승인 프롬프트가 뜬다. 고장이 아니라 정상 동작이다.**
1단계로 넘어가기 전에 이 사실을 사용자에게 먼저 말한다. 모르면 첫 프롬프트에서 고장으로
오해하고 멈춘다.

- 온보딩 한 번에 **프롬프트가 여러 번 뜬다.** 확인한 시험에서 `Get-Content`·`rg`·
  `git status`·`python`이 각각 승인을 요구했다.
- 승인할지는 사용자가 정한다. 에이전트가 권한 모드를 올려 우회하지 않는다.

## 1단계 — 호스트별 1번과 공통 항목을 스크립트로 한 번에

```text
python scripts/check_env.py
```

표로 돌려준다. 결과를 다음 단계에 값으로 넘겨야 하면 `--json`을 붙인다.
`--network-timeout`은 기본 5초이고, 느린 사내망이면 올린다. 저장소 밖에서 실행해
루트를 못 찾으면 `--repo-root`로 준다.

이 스크립트는 상태를 바꾸지 않는다. 8번 디렉터리도 **만들지 않고 만들 수 있는지만** 본다.
10번도 로그인 상태를 읽기만 한다 — **스크립트가 로그인하지 않는다.**

codex 표의 맨 위가 10번이다. **10번이 실패면 거기서 멈추고** 나머지는 확인 불가로 적는다.
Claude Code 표에는 10번이 없으며 이것은 **해당 없음**이지 실패가 아니다.

| # | 항목 | 확인 방법 | 통과 기준 | 실패 시 조치 | 담당 |
| --- | --- | --- | --- | --- | --- |
| 10 | codex 로그인 | `codex login status` | 출력이 로그인됨을 가리킨다 — 로그인된 환경에서 관찰된 문자열은 `Logged in using ChatGPT`이고, 안 된 환경은 `Not logged in`이다. **종료코드로 가르지 않는다**: 로그인 여부와 무관하게 0이 나온 사례가 있어 종료코드로 판정하면 안 된 환경도 통과로 나온다 | 로그인 방법(`codex login`)을 안내하고 **멈춘다**. **에이전트가 로그인하지 않는다** — 자격 증명이고 브라우저 상호작용이 필요하다 | 에이전트가 확인, 로그인은 **사용자** |
| 1 (codex) | 플러그인 설치·활성 | `codex plugin list` | 출력에 `liverock-toolkit@liverock`이 있고 `installed, enabled` | `codex plugin add liverock-toolkit@liverock`을 사용자에게 제시한다. 설치 절차는 저장소 `README.md`에 있고 여기서 다시 쓰지 않는다 | 에이전트 |
| 1 (Claude Code) | 플러그인 설치·활성 | `claude plugin list` | 해당 플러그인 블록의 `Status`가 `enabled`다 | 아래 Claude Code 설치·갱신 경로를 사용자에게 제시한다 | 에이전트 |
| 2 | Python 3 | `python --version` | 메이저 버전 3 이상 | Python 3 설치를 안내하고 멈춘다. 설치는 사용자 환경 변경이라 에이전트가 하지 않는다 | 에이전트 |
| 3 | 네트워크 | OpenAlex 공개 엔드포인트에 짧은 타임아웃으로 한 번 요청 | 응답이 온다(HTTP 상태는 무관 — 도달 여부만 본다) | 프록시·방화벽을 사용자에게 알린다. 막혀 있으면 논문 탐색이 안 되므로 `literature-analysis`를 쓸 수 없다고 명시한다 | 에이전트 |
| 8 | 실행 기록 디렉터리 | `.agents/orchestration/`에 쓸 수 있는지, `git check-ignore`가 덮는지 | 쓰기 가능하고 `.gitignore` 적용됨 | 디렉터리가 없으면 **만들겠다고 먼저 말하고 승인을 받아** 만든다. `.gitignore`가 안 덮으면 저장소 규칙 변경이므로 제안만 하고 사용자 답을 받는다 | 에이전트 |

스크립트가 `확인 불가`를 내면 그대로 표에 옮긴다. stderr 진단에 원인이 한 줄로 남아 있으니
그 줄도 사용자에게 전하되, **아래 「오류를 전하는 순서」를 지킨다.**

표 아래에 나오는 `provider CLI 실행 경로` 절은 9번에서 쓴다. 여기서는 판정하지 않고
값만 들고 간다.

### Claude Code 설치·갱신 경로

Claude Code의 marketplace 설치는 `claude plugin marketplace add <source>` 뒤에
`claude plugin install liverock-toolkit@<marketplace-name>`을 실행한다. 갱신은
`claude plugin marketplace update <marketplace-name>` 뒤 현재 세션에서 `/reload-plugins`를
실행하거나 새 세션을 시작한다. 이는 Claude Code 공식 플러그인 문서의 marketplace 추가·설치·갱신
절차다.

다만 현재 이 저장소에는 Claude Code가 요구하는 `.claude-plugin/marketplace.json`이 없다. 따라서
이 저장소에 대응하는 `<source>`와 `<marketplace-name>`을 추측해 적지 않는다. 배포용 Claude
marketplace가 준비되기 전에는 저장소 루트에서 `claude --plugin-dir ./plugins/liverock-toolkit`로
로컬 플러그인을 직접 로드하고, 본문 변경은 `/reload-plugins` 또는 새 세션으로 반영한다.
`check_env.py`도 이 매니페스트의 `name`을 읽을 수 있을 때만 설치 명령에 쓰며, 없거나 읽지 못하면
같은 로컬 로드 경로만 제시한다.

개발 중 설치 없이 저장되는 스킬 경로는 codex가 `.agents/skills/<이름>/`, Claude Code가
`.claude/skills/<이름>/`이다. 이 플러그인처럼 배포할 스킬은 두 호스트 모두
`plugins/<플러그인>/skills/`에 두고 각 호스트의 플러그인 설치·활성 절차를 거친다.

## 오류를 전하는 순서

**뜻과 조치를 먼저 말하고, 원문은 그 뒤에 붙인다.** 원문을 지우지는 않는다.

```text
(1) 이게 무슨 뜻인지  →  (2) 지금 무엇을 하면 되는지  →  (3) 원문 메시지
```

이 순서인 이유는 **읽는 사람이 codex·claude CLI를 모르기 때문이다.** `CreateProcessAsUserW
failed: -1073283067`을 먼저 던지면 사용자는 뜻을 모른 채 자기가 뭘 잘못했다고 생각하고
멈춘다. 반대로 원문을 빼 버리면 나중에 검색하거나 다른 사람에게 물을 때 쓸 것이 없어진다.
그래서 **지우는 게 아니라 순서만 뒤집는다.** 규칙의 목적이 "원문 감추기"가 아니라 "먼저
읽을 것을 앞에 두기"이므로, 사용자가 원문을 직접 들고 와서 묻는 경우에도 답은 뜻과 조치가
먼저다.

뜻과 조치는 [`references/errors.md`](references/errors.md)에 정리돼 있다. **점검 중 실패가
나왔을 때, 또는 사용자가 오류 메시지를 들고 왔을 때만 연다.** 평소에는 읽지 않는다.
거기 없는 메시지는 뜻을 지어내지 말고 그 파일의 「표에 없는 메시지」를 따른다.

## 2단계 — 4·5는 `paseo` CLI로 본다

여기가 이 스킬이 있는 가장 큰 이유다. **세션에 Paseo 도구가 붙어 있는지로 판정하지
않는다.** 확인한 codex 세션의 도구 목록에 Paseo 도구는 하나도 없었고, 그런데도 앱과 데몬은
정상이었다. 도구가 붙기를 기다리면 멀쩡한 환경을 실패로 적고 거기서 멈춘다. **codex와
Claude Code는 셸을 쓸 수 있으므로 4·5·6·9는 `paseo` 명령으로 판정한다.**

4번은 데몬이 살아 있는지를, 5번은 이 셸에서 데몬에 실제로 질의가 되는지를 본다. 둘을
나누는 이유는 조치가 다르기 때문이다 — 4번 실패는 앱을 설치하거나 실행하는 일이고,
5번 실패는 이미 떠 있는 데몬을 다시 세우는 일이다. 10·1·2·3·8을 스크립트로 먼저 돌리는
것은 그것이 빠르고 사용자 손을 안 빌리기 때문이지, 4·5가 덜 중요해서가 아니다.

| # | 항목 | 확인 방법 | 통과 기준 | 실패 시 조치 | 담당 |
| --- | --- | --- | --- | --- | --- |
| 4 | paseo CLI와 데몬 | `paseo status` | 명령이 실행되고, 출력의 `Local Daemon`이 `running`이며 `Connected Daemon`이 `reachable`이다 | 명령을 못 찾으면 Paseo 앱 설치와 PATH 등록을, 데몬이 안 떠 있으면 앱 실행을 알리고 멈춘다. 앱 설치·실행은 에이전트가 하지 않는다 | 에이전트가 확인, 설치·실행은 **사용자** |
| 5 | 데몬 질의 | `paseo ls --json` | JSON 배열이 나온다. 에이전트가 하나도 없어 `[]`여도 통과다 — 여기서 보는 것은 목록의 내용이 아니라 질의가 되는지다 | 아래 방법을 제시하고 멈춘다 | 에이전트가 확인, 재시작은 **사용자** |

5번이 실패일 때 사용자에게 전할 것:

1. `paseo status`는 통과했는데 조회만 실패했다는 사실과 **오류 원문**을 전한다. 4번과
   5번의 판정이 갈렸다는 것 자체가 다음에 볼 자리를 좁혀 준다.
2. 데몬을 다시 세운다 — `paseo restart`, 또는 Paseo 앱을 껐다 켠다.
3. 다시 `paseo status`와 `paseo ls --json`을 돌려 4번부터 확인한다.

**에이전트가 데몬을 임의로 재시작하지 않는다.** 데몬은 이 저장소 밖에서 돌고 있는 다른
작업까지 들고 있어서, 재시작하면 그쪽이 함께 끊긴다. 승인을 받은 뒤에 한다.

## 3단계 — 9는 provider가 실제로 실행되는지 본다

4·5가 통과했을 때만 여기로 온다. **데몬은 정상인데 provider CLI 실행 파일만 못 찾는
상태**가 여기서 걸린다. 이때 워커 기동(`paseo run`)이 실패하는데 사용자는 무엇이 없어서
실패했는지 알 수 없다.

| # | 항목 | 확인 방법 | 통과 기준 | 실패 시 조치 | 담당 |
| --- | --- | --- | --- | --- | --- |
| 9 | provider 실행 경로 | `paseo provider ls --json`으로 각 provider의 `status`를 본다 | 쓰려는 provider의 `status`가 `available`이다 | `paseo provider diagnostic <provider> --json`으로 **데몬이 실제로 찾아본 경로**를 본다. 거기서 못 얻으면 1단계 스크립트 출력의 `provider CLI 실행 경로` 절에서 실행 파일 경로를 찾는다. 찾은 값을 사용자에게 그대로 보여 주고 Paseo 설정의 해당 provider 실행 경로에 넣으라고 안내한다. 어느 쪽에서도 못 찾았으면 **찾아본 위치 목록**을 전한다 | 에이전트가 경로를 찾아 제시하고, **설정 반영은 사용자** |

`diagnostic`은 데몬이 쓰는 PATH와 `Resolved path`·`Status`를 함께 낸다. 정상으로 관찰된
값은 `Status: Ready`다. `Resolved path`가 안 나오면 실행 파일을 못 찾은 것이므로 아래
스크립트로 경로를 찾아 제시한다.

**"못 찾았다"로 끝내지 않는다.** 이 항목의 목적은 판정이 아니라 **사용자가 Paseo 설정에
넣을 값을 손에 쥐여 주는 것**이다. 경로를 직접 찾아 헤매게 만들면 여기서 온보딩이 멈춘다.

1단계를 건너뛰고 들어왔거나 그때 경로를 못 받았으면 스크립트를 다시 돌린다.

```text
python scripts/check_env.py
```

Windows에서 npm으로 깐 경우 `codex`(확장자 없음)·`codex.cmd`·`codex.ps1`이 함께 깔린다.
**확장자 없는 쪽을 설정에 넣으면 실행되지 않는다.** 스크립트는 실행 가능한 쪽을 골라서
내므로, 스크립트가 낸 경로를 그대로 쓰게 한다.

`status`가 `available`이 아닌 provider를 프로필이 가리키고 있으면 그 프로필은 쓸 수 없다.
9번이 실패면 7번은 **확인 불가**로 적는다 — 프로필이 등록돼 있어도 그 워커는 안 뜬다.

## 4단계 — 6·7은 워크스페이스와 프로필을 본다

4·5·9가 통과했을 때만 여기로 온다. 하나라도 실패·확인 불가면 6·7을 **확인 불가**로 적고
앞 단계 결과와 함께 보고한 뒤 멈춘다.

| # | 항목 | 확인 방법 | 통과 기준 | 실패 시 조치 | 담당 |
| --- | --- | --- | --- | --- | --- |
| 6 | 워크스페이스 | `paseo workspace ls --json` | `cwd`가 사용자의 연구 디렉터리인 워크스페이스가 하나 이상 있다 | 어느 디렉터리를 쓸지 사용자에게 묻고, 답을 받은 뒤 만든다. 어느 경로인지 모르는 채로 만들지 않는다 | 에이전트 |
| 7 | 프로필 등록 | **프로필을 조회하는 `paseo` 명령이 없다.** `profile-setup`에 넘겨 등록된 목록을 받는다 | 등록된 프로필이 하나 이상임을 확인했다 | `profile-setup`으로 넘긴다 (아래) | 에이전트 |

6번은 조회만 하는 항목이다. 워크스페이스를 새로 만드는 것은 조회가 아니므로, 대상 경로를
사용자에게 확인받은 뒤 `paseo workspace create --path <경로> --isolation local`로 만든다.
워크스페이스를 생략하고 워커를 띄우면 엉뚱한 새 워크스페이스가 생기므로, 여기서 경로를
못 정했으면 확인 불가로 남긴다.

### 7번이 실패면

프로필이 하나도 없으면 팀장 에이전트가 위임할 곳을 고를 근거가 없어서 워커를 띄워도
라우팅이 성립하지 않는다. **`profile-setup` 스킬로 넘긴다.** 7번은 CLI로 직접 볼 수 없어
판정 근거가 그쪽 결과뿐이므로, 목록을 받지 못했으면 통과가 아니라 **확인 불가**로 적는다.

사용자에게 알릴 것은 두 가지뿐이다.

- `profile-setup`이 저가형·고가형 두 프리셋 세트를 가지고 있다.
- 기본 제안은 저가형이다.

**등록 절차 자체를 여기에 옮겨 적지 않는다.** provider 조회, 모델 선택, mode 확인, 설정
반영 순서는 전부 `profile-setup`에 있다. 같은 절차가 두 벌이면 한쪽만 고쳐졌을 때 어느
쪽이 맞는지 알 수 없고, 고칠 곳이 두 군데가 된다. 등록이 끝나면 이 스킬로 돌아와 7번을
다시 조회해 판정한다.

## 5단계 — 보고

현재 호스트에 해당하는 항목을 **한 표로** 낸다. 통과한 것만 추리거나 실패한 것만 내지 않는다 — 사용자가
알아야 하는 것은 "무엇이 남았나"이고, 그건 전체를 봐야 보인다.

```text
| # | 항목 | 판정 | 근거 | 다음 동작 |
```

표 아래에 **지금 사용자가 할 일 하나**를 적는다. 여러 개가 남았으면 순서상 가장 앞의 것
하나만 적는다. 익숙하지 않은 사용자에게 할 일 다섯 개를 한꺼번에 주면 어디서부터 손댈지
모른 채 멈춘다.

전부 통과했으면 그 사실을 적고, 바로 쓸 수 있는 스킬을 한 줄로 안내한다 — 논문은
`literature-analysis`, 실험 계획은 `experiment-planning`, 여러 작업을 나눠 돌리는 것은
`research-orchestration`과 `agent-orchestration`.

## 막혀서 들어온 경우

다른 스킬이 진행하지 못해 이쪽으로 왔으면 현재 호스트에 해당하는 항목을 처음부터 다 돌린다. 증상만 보고
한 항목을 찍어 고치면 그 앞의 원인이 남아 같은 자리에서 다시 막힌다.

| 증상 | 먼저 볼 항목 |
| --- | --- |
| 워커가 안 뜬다, `paseo` 명령이 안 먹거나 조회가 실패한다 | 4 → 5 |
| 조회는 되는데 워커 생성만 실패한다, provider가 `unavailable`이다 | 9 |
| 워커는 뜨는데 엉뚱한 디렉터리에서 돈다 | 6 |
| 위임할 프로필을 못 고른다 | 7 |
| 논문 검색이 실패한다 | 3 → 2 |
| 스킬이 아예 발동하지 않는다 | 1 |
| codex가 로그인을 요구한다, 플러그인 목록이 통째로 비어 있다 | 10 |
| 실행 기록이 안 남거나 git에 잡힌다 | 8 |

이 표는 어디부터 볼지를 정할 뿐이고, 판정은 열 항목 전부에 대해 적는다.

사용자가 오류 메시지를 들고 왔으면 그것부터 위 「오류를 전하는 순서」로 풀어 준 뒤 점검에
들어간다. 뜻을 모르는 채로 점검 열 개를 시작하면 사용자는 자기 질문이 무시됐다고 본다.
