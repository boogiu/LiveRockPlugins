# LiveRock 스킬 작성 가이드

이 플러그인의 스킬을 새로 만들거나 고칠 때 읽는다. 사용자에게 발동되는 스킬이 아니라
`skills/` 아래를 채우는 사람이 보는 규격서다.

아직 `skills/`는 비어 있다. 화학공학 연구 업무에서 실제로 반복되는 일이 무엇인지는
사용자의 업무 리포트를 받아 정하고, 그때 이 문서의 규격에 맞춰 스킬을 채운다.
아래 예시는 형식을 보여주려고 든 것이지 만들기로 정해진 스킬 목록이 아니다.

## 0. 무엇을 스킬로 만드나

스킬은 **에이전트가 매번 다시 알아내야 하는 것**을 한 번 적어 두는 자리다. 판단 기준은
"유용한가"가 아니라 "반복되는가, 그리고 매번 같은 방식으로 해야 하는가"다.

스킬로 만들 만한 것:
- 여러 단계를 정해진 순서로 밟아야 하고, 순서를 틀리면 결과가 망가지는 작업
- 출력 형식이 정해져 있어서 매번 같은 서식으로 나와야 하는 작업
- 도구·파일·설정의 위치나 사용법을 모르면 시작할 수 없는 작업
- 도메인 지식이 있어야 옳고 그름을 가릴 수 있는 작업

스킬로 만들 필요가 없는 것:
- 한 번 쓰고 마는 일회성 작업
- 에이전트가 기본 도구만으로 이미 잘 하는 일. 이런 건 스킬을 만들어도 발동하지 않는다

## 1. 쓰기 전에 정할 네 가지

초안을 잡기 전에 이 네 가지의 답을 받아 둔다. 답이 비면 나중에 전부 다시 쓴다.

1. **이 스킬은 무엇을 할 수 있게 하나** — 완료된 상태를 한 문장으로.
2. **언제 발동해야 하나** — 사용자가 실제로 칠 법한 발화를 그대로 수집한다. 상상해서
   다듬은 문장이 아니라 실제 표현이어야 한다. 이게 4절의 `description`이 된다.
3. **출력이 무엇인가** — 파일인지 화면 보고인지, 서식이 정해져 있는지.
4. **무엇을 확인해야 잘 된 것인가** — 결과가 맞았는지 가릴 방법. 수치·파일 존재·형식처럼
   객관적으로 확인 가능한 것이면 그대로 적고, 판단이 필요한 것이면 누가 무엇을 보고
   판정하는지 적는다.

이미 대화 중에 그 작업을 한 적이 있다면 거기서 먼저 뽑는다 — 쓴 도구, 밟은 순서,
사용자가 중간에 고쳐 준 지점, 주고받은 파일 형식. 사용자에게는 빈칸만 묻는다.

## 2. 스킬의 구조

```
skills/<skill-name>/
├── SKILL.md         (필수) frontmatter + 본문
├── scripts/         실행 코드. 결정적이고 반복되는 계산·변환
├── references/      필요할 때만 읽는 상세 문서
└── assets/          산출물에 들어가는 파일 (템플릿, 서식)
```

폴더 이름과 `SKILL.md`의 `name`은 kebab-case로 같게 쓴다.

`README.md`, `CHANGELOG.md` 같은 부가 문서는 스킬 폴더에 두지 않는다. 설명할 것이 있으면
`SKILL.md` 본문에 쓰고, 길면 `references/`로 내린다.

## 3. 세 단계로 나뉘어 읽힌다

이 구조가 있는 이유는 컨텍스트 예산 때문이다. 세 층이 각각 다른 시점에 읽힌다.

| 층 | 언제 읽히나 | 분량 |
| --- | --- | --- |
| `name` + `description` | 항상 — 발동 여부를 판단할 때 | 짧게 |
| `SKILL.md` 본문 | 스킬이 발동한 뒤 | 500줄 미만 |
| `scripts` / `references` / `assets` | 본문이 지시한 시점에만 | 제한 없음 |

여기서 나오는 결론 두 개가 중요하다.

- **"언제 쓰는가"는 전부 `description`에 넣는다.** 본문의 "이럴 때 사용하세요" 절은
  이미 발동한 뒤에만 읽히므로 아무 효과가 없다.
- **본문이 500줄에 가까워지면 쪼갠다.** 실행 코드는 `scripts/`, 상세 문서는
  `references/`로 내리고, 본문에는 **무엇을 언제 읽어야 하는지**를 남긴다.

분리한 파일은 반드시 본문에서 링크하고 읽는 시점을 함께 적는다. 참조 깊이는 `SKILL.md`
기준 한 단계까지다 — `references/a.md`가 다시 `references/b.md`를 읽게 하지 않는다.

변형이 여러 개인 스킬은 변형별로 파일을 나눈다. 본문은 고르는 법만 담고, 고른 것 하나만
읽히게 한다.

```
<skill-name>/
├── SKILL.md              공통 절차 + 어느 것을 고를지
└── references/
    ├── variant-a.md
    └── variant-b.md
```

## 4. frontmatter

`name`과 `description` 둘만 쓴다.

```yaml
---
name: skill-name
description: 무엇을 하는지. 그리고 어떤 요청일 때 쓰는지. "실제 발화1", "실제 발화2" 같은 요청에 사용한다.
---
```

`description`은 발동을 결정하는 **유일한** 근거다. 두 가지를 다 담아야 한다.

- **무엇을 하는가** — 한 문장.
- **언제 쓰는가** — 사용자가 실제로 쓰는 한국어 표현을 따옴표로 나열한다. 격식체와
  구어체를 섞고, 줄임말과 실제로 나오는 오타까지 포함한다.

에이전트는 스킬을 **과소 발동**하는 경향이 있다. 그래서 `description`은 조심스럽게
쓰기보다 적극적으로 쓴다. "~에 사용할 수 있다"가 아니라 "~ 요청이면 반드시 이 스킬을
쓴다"처럼 적는다.

경계가 겹치는 스킬이 있으면 어느 쪽이 맡는지를 `description`에 직접 적는다.
`profile-setup`의 `description` 마지막 문장이 그 예다 — 인접 스킬의 이름을 부르고
경계를 긋는다.

## 5. 본문 작성 패턴

**명령형으로 쓴다.** "~하는 것이 좋습니다"가 아니라 "~한다".

**출력 형식이 정해져 있으면 서식을 그대로 박는다.** 견본이 길거나 여러 개면
`references/FORM.md`에 `##` 절 단위로 두고, 본문에서는 읽을 절과 읽는 시점을 지정한다.
실행 경로·권한·승인·성공 여부를 결정하는 지시와, 참조 파일을 읽기 **전에** 적용돼야 하는
지시는 참조로 내리지 말고 본문에 남긴다.

**분기가 있으면 표로 만든다.** 조건과 다음 동작을 나란히 놓는다.

| 상황 | 다음 동작 |
| --- | --- |
| A | ... |
| B | ... |

**예시는 입력과 출력을 짝으로 보인다.**

```markdown
입력: 반응기 온도 데이터 CSV, 컬럼명이 제각각
출력: 표준 컬럼명으로 정규화된 CSV + 매핑 로그
```

**같은 코드를 매번 다시 짜게 하지 않는다.** 스킬을 쓸 때마다 에이전트가 비슷한 스크립트를
새로 작성한다면 그건 `scripts/`에 넣으라는 신호다. 한 번 써서 넣고 본문은 그걸 쓰라고만
지시한다.

## 6. 작성 스타일

**왜 그래야 하는지를 설명한다.** 대문자 MUST, ALWAYS, NEVER를 쓰고 있다면 멈추고 다시
본다. 규칙만 던지면 상황이 조금만 달라져도 엉뚱하게 적용된다. 이유를 알면 판단할 수 있다.

나쁜 예 — `ALWAYS 물질수지를 먼저 확인할 것`
좋은 예 — `물질수지를 먼저 확인한다. 여기가 안 맞으면 뒤의 계산이 전부 틀린 값 위에
쌓이므로, 이후 단계를 아무리 잘해도 결과를 못 쓴다.`

**특정 예시에 맞춘 규칙을 쓰지 않는다.** 만들 때 본 두세 개 사례에만 맞는 규칙을 박으면
그 사례 밖에서 못 쓴다. 규칙을 하나 쓸 때마다 "이게 다른 경우에도 맞나"를 본다.

**안 쓰이는 문장은 지운다.** 읽히지만 아무 동작도 바꾸지 않는 문단은 컨텍스트만 먹는다.

**초안을 쓰고 나서 다시 본다.** 한 번에 완성된 스킬은 없다. 초안을 낸 뒤 처음 보는 눈으로
읽고, 모호한 곳과 빠진 분기를 찾는다.

## 7. 초안 다음

초안이 나오면 **실제 발화로 시험한다.** 1절 2번에서 모은 발화를 그대로 던져서, 스킬이
발동하는지와 결과가 4번의 확인 기준을 통과하는지 본다. 발동하지 않으면 본문이 아니라
`description`을 고친다. 발동은 하는데 결과가 틀리면 본문을 고친다.

## 8. 이 저장소에서만 적용되는 제약

- **`liverock-toolkit`은 codex와 Claude Code를 함께 지원한다.** 매니페스트는
  `.codex-plugin/plugin.json`, `.claude-plugin/plugin.json`, `.agents/plugins/marketplace.json`,
  `.claude-plugin/marketplace.json` 네 개를 둔다. `commands/`, `agents/`, `hooks/`,
  `.mcp.json`은 claude 전용 컴포넌트라 codex가 읽지 않으므로 여기서는 쓰지 않는다.
  핵심 동작은 전부 `SKILL.md`에 둔다.
- **파일 참조는 스킬 디렉터리 기준 상대 경로로 쓴다.** `${CLAUDE_PLUGIN_ROOT}`는 codex에
  존재하지 않는다.
- **스크립트는 그 스킬 안(`skills/<name>/scripts/`)에 둔다.** 둘 이상의 스킬이 같은
  스크립트를 쓰게 되는 순간 플러그인 루트의 `scripts/`로 올린다. 스킬이 다른 스킬 폴더의
  파일을 참조하는 상태로 남기지 않는다.
- **홈 경로, 드라이브 문자, 저장소 절대 경로를 하드코딩하지 않는다.** 실행 환경에서 구한다.
- **인코딩** — `.md`, `.json`, `.ps1`, `.py`는 UTF-8(BOM 없음)로 쓴다. `.bat`/`.cmd`에는
  한글을 쓰지 않는다. 한글이 든 `.ps1`은 pwsh 7 기준으로 쓴다.
- **스킬을 추가하면 두 호스트의 마켓플레이스 매니페스트 등록 상태와 두 `plugin.json`의
  `version`을 같이 본다.** 버전은 `main`에 머지하기 직전에 올리고, 올릴 값은 사용자에게
  확인받는다.

## 9. 제출 전 점검

- [ ] `SKILL.md`에 frontmatter가 있고 `name`·`description` 둘만 있다
- [ ] `name`이 폴더 이름과 같고 kebab-case다
- [ ] `description`에 "무엇을"과 "언제"가 다 있고, 실제 한국어 발화가 들어 있다
- [ ] 본문에 "이럴 때 사용" 절이 남아 있지 않다
- [ ] 본문이 500줄 미만이다
- [ ] 분리한 파일이 전부 본문에서 링크돼 있고 읽는 시점이 적혀 있다
- [ ] 참조 깊이가 한 단계를 넘지 않는다
- [ ] 절대 경로와 `${CLAUDE_PLUGIN_ROOT}`가 없다
- [ ] 스킬 폴더에 `README.md`/`CHANGELOG.md`가 없다
- [ ] 모든 파일이 UTF-8(BOM 없음)이다
- [ ] 실제 발화로 발동과 결과를 확인했다
